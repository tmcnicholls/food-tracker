# Weekly Food Planner

A free, private, mobile-first PWA to keep a
simple weekly food plan — no calorie counting, no accounts, no backend.
Generate a realistic Tuesday–Monday meal plan, edit it to match what you
actually ate, set a RAG status per day, and copy the result straight into
Apple Notes.

Everything runs entirely in the browser. Data is stored only in
`localStorage` on your device; nothing is ever sent to a server.

## Features

- Seven-day plan (Breakfast, Lunch, Tea, Snacks) generated from a bundled
  meal library — no network calls.
- Configurable week start (any weekday, or an exact date), defaulting to
  Tuesday.
- Great / Medium / Poor consistency profile that shapes the suggested meal
  pattern, not a judgement of the user.
- Optional Saturday takeaway (Chinese, Indian, Kebab, Pizza, Greek gyros).
- Inline editing, per-meal confirm/skip, and a RAG status per day.
- One-tap **Copy plan** for pasting into Apple Notes, with a clipboard
  fallback.
- Installable on iOS via Safari's **Add to Home Screen**, with offline
  support after the first load.

## Project structure

```
index.html          App shell / markup
css/styles.css       Mobile-first styles (light + dark)
js/mealLibrary.js    Bundled meal data (breakfast/lunch/tea/snacks/takeaway)
js/dates.js          Local-calendar-date helpers (no UTC day-shift bugs)
js/rng.js            Seeded PRNG + weighted random pick helpers
js/generator.js      Deterministic weekly meal-plan generator
js/storage.js        localStorage persistence (with in-memory fallback)
js/app.js            UI controller: rendering + event wiring
manifest.json        Web app manifest (PWA metadata/icons)
sw.js                Service worker: caches the app shell for offline use
icons/               App icons (generated by scripts/generate_icons.py)
scripts/generate_icons.py          Regenerates icons/*.png without any dependencies
scripts/update_sw_cache_version.py Keeps sw.js's CACHE_NAME in sync with APP_SHELL file contents
.githooks/pre-commit                Runs the script above automatically before every commit
```

No build step is required — it's plain HTML/CSS/JS served as static files.

## Running locally

Because `js/app.js` is loaded as an ES module, open it over `http://`, not
`file://` (module scripts are blocked on the `file:` origin in most
browsers). Any static file server works, for example:

```bash
cd food-tracker
python3 -m http.server 8080
# then open http://localhost:8080 in your browser
```

## Deploying to GitHub Pages

1. **Create the repository.** Push this project to a new GitHub repository
   (public, so Pages is free), e.g. `food-tracker`.

   ```bash
   cd food-tracker
   git init
   git add .
   git commit -m "Initial commit"
   git branch -M main
   git remote add origin https://github.com/<your-username>/food-tracker.git
   git push -u origin main
   ```

2. **Enable Pages.** In the repository on GitHub: **Settings → Pages →
   Build and deployment → Source**, choose **Deploy from a branch**, then
   pick the `main` branch and the `/ (root)` folder. Save.

3. **Wait for the first build.** GitHub shows a URL once it's live, in the
   form:

   ```
   https://<your-username>.github.io/food-tracker/
   ```

   This project uses only relative paths (`css/...`, `js/...`,
   `icons/...`, and a relative `manifest.json`/`sw.js`), so it works
   correctly under that `/food-tracker/` subpath without any extra
   configuration — no `<base>` tag or path rewriting needed.

4. **Confirm HTTPS.** GitHub Pages serves everything over HTTPS by default,
   which is required for both the install prompt and the service worker to
   work on iOS.

## Installing on iPhone (Add to Home Screen)

1. Open the GitHub Pages URL in **Safari** on the iPhone (it must be Safari,
   not Chrome, for the install flow to appear).
2. Tap the **Share** icon (square with an arrow).
3. Scroll down and tap **Add to Home Screen**.
4. Confirm the name and tap **Add**.

The app now opens full-screen from the home screen, uses the bundled icon
and theme colour, and keeps working offline after it's been opened once
while online.

## Updating the deployed app

1. Make your changes locally and test with the local server above.
2. Commit and push to `main`:

   ```bash
   git add .
   git commit -m "Describe the change"
   git push
   ```

3. GitHub Pages redeploys automatically within a minute or two.

You do **not** need to manually bump anything in `sw.js` — see below.

### `sw.js`'s CACHE_NAME updates itself

`CACHE_NAME` in `sw.js` is a hash of the actual contents of every file
listed in its `APP_SHELL` array (`index.html`, `css/styles.css`, every
`js/*.js` file, `manifest.json`, the icons). A pre-commit hook runs
`scripts/update_sw_cache_version.py` automatically before every commit:
if any of those files changed, it recomputes the hash, rewrites
`CACHE_NAME`, and stages the updated `sw.js` into the same commit. If
nothing in `APP_SHELL` changed, it's a no-op.

This replaces an earlier hand-maintained version string (`v1`, `v2`, ...),
which was once forgotten on a real deploy and shipped a stale cached app
shell. The hash can't be forgotten the same way — it's not something
anyone needs to remember to do.

**One-time setup per clone** (already done in this working copy): git
doesn't run hooks from a tracked directory by default, so point it at the
one in this repo:

```bash
git config core.hooksPath .githooks
```

You can also run the script by hand at any time — e.g. to check it's
up to date without committing:

```bash
python3 scripts/update_sw_cache_version.py
```

### How updates are detected on an installed Home Screen app

`sw.js` uses a **network-first** fetch strategy: every request — including
the HTML shell — tries the network first and only falls back to the cached
copy when offline. This means a plain reload while online always fetches
current content; the cache exists purely as an offline safety net, not as
the primary source.

For the service worker script itself, `js/app.js` proactively calls
`registration.update()`:

- once when the app loads,
- again whenever the app returns to the foreground (`visibilitychange` /
  `pageshow` — the common case for an installed iOS Home Screen app, which
  is almost always *resumed* rather than cold-launched),

throttled to at most once a minute so it never polls excessively, and
wrapped so a failed check (e.g. offline) never breaks normal use.

When an update is found, the new service worker installs but **does not
activate automatically** — it waits. The app then shows a small banner:

> A new version is available. **Update now**

Tapping **Update now** tells the waiting worker to take over, and the page
reloads itself exactly once to pick up the new version. Nothing happens
automatically in the background without this prompt, specifically so an
update can never interrupt something you're in the middle of typing or
confirming. If you ignore the banner, the app keeps working exactly as
before on the current version until you choose to update.

### Known limitations (iOS / GitHub Pages)

- GitHub Pages doesn't allow custom response headers, so we can't set
  `Cache-Control: no-cache` on `sw.js` at the HTTP level. This isn't a
  practical problem: browsers are spec-required to always bypass HTTP
  cache for the top-level service worker script's own update check, so
  this doesn't block update detection — it's listed here only because it's
  a constraint we can't change, not one we need to.
- iOS Safari's background service-worker update checks for installed
  Home Screen apps are known to be infrequent/inconsistent in general.
  The `visibilitychange`/`pageshow`-triggered `update()` calls above are
  the mitigation: as long as the app is opened and foregrounded, an update
  check happens within that minute's throttle window, rather than relying
  solely on the browser's own (rarer) background schedule.
- The update banner only appears once the new worker reaches the
  `installed` state, which still requires an actual network fetch of
  `sw.js` to succeed — on a persistently offline device, no update can be
  detected until connectivity returns (expected, and the app continues to
  work offline on whatever version is already installed).

## Regenerating icons

Icons are generated by a small, dependency-free script (no Pillow/ImageMagick
required) that draws a simple plate-and-cutlery glyph directly as PNG bytes:

```bash
python3 scripts/generate_icons.py
```

This overwrites `icons/icon-{32,180,192,512}.png`. Re-run it if you want to
change the colours (edit the `BG`/`FG`/`ACCENT` constants at the top of the
script) or add a new size.

## Privacy

- No accounts, no analytics, no third-party APIs.
- All plans, preferences and edits live in this browser's `localStorage`
  only, on this device.
- Clearing the browser's site data (or using the in-app **Clear all saved
  plans and preferences** button) permanently deletes everything saved
  by the app, with no way to recover it.

## Browser support notes

- Built and tested against current iOS Safari and desktop Chrome/Safari/
  Firefox.
- Uses the native `<dialog>` element for confirmations, with a
  `window.confirm()` fallback for older browsers that lack it.
- Uses the async Clipboard API for **Copy plan**, with a visible
  select-and-copy textarea fallback if clipboard access is unavailable.
